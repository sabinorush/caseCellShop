     Idempotência no checkout + healthcheck

     Context

     Hoje a única proteção contra compra duplicada é o estado local isSubmitting
     em
     apps/web/src/components/BuyForm.tsx:26, que desabilita o botão "Comprar"
     enquanto a
     requisição está em voo. Isso é proteção de UI, não de servidor:

     - apps/api/src/checkout/checkout.service.ts:28 gera um randomUUID() novo a
       cada chamada e
       apps/api/src/products/products.service.ts:30 decrementa o estoque — a API
       não tem
       nenhuma noção de "essa compra eu já processei".
     - Qualquer caminho que escape do isSubmitting gera compra dupla: recarregar
       a página e
       clicar de novo, duas abas, curl, ou — o caso mais provável — um retry 
       após
       timeout/erro de rede. Depois do trabalho da sessão anterior, o client.ts
       aborta em
       8s (REQUEST_TIMEOUT_MS) e a UI incentiva o retry; se a API processou a
       compra e só a
       resposta se perdeu, o retry hoje debita o estoque duas vezes.

     Objetivo: o servidor passa a ser a fonte da verdade da unicidade da compra.
     Cada tentativa
     carrega um Idempotency-Key; repetir a requisição com a mesma chave devolve
     exatamente o
     mesmo pedido, sem tocar no estoque. Sem Redis — um store em memória no
     próprio processo,
     no mesmo espírito do catálogo em memória que já existe.

     Junto vai um GET /health simples, que hoje não existe (a única forma de
     saber se a API
     está de pé é bater em /products).

     Decisões confirmadas: chave no header Idempotency-Key; duplicata concluída
     → replay
     do mesmo 201, duplicata em voo → 409; no front a chave é por tentativa e é
     reusada em
     falha incerta; healthcheck com controller próprio, sem @nestjs/terminus.

     1. API — store de idempotência

     Novo: apps/api/src/common/idempotency-store.ts

     Classe pura, sem decorators do Nest — igual ao InsufficientStockError, que
     também mora
     numa classe simples. Isso mantém os specs no padrão atual
     (checkout.service.spec.ts
     instancia new ProductsService() direto, sem TestingModule).

     export type BeginResult<T> =
       | { status: 'new' }
       | { status: 'in-flight' }
       | { status: 'replayed'; value: T }
       | { status: 'fingerprint-mismatch' };

     export class IdempotencyStore<T> {
       constructor(options?: { ttlMs?: number; maxEntries?: number });
       begin(key: string, fingerprint: string): BeginResult<T>;
       complete(key: string, value: T): void;
       release(key: string): void;
     }

     Entrada interna: { status: 'in-flight' | 'completed'; fingerprint: string; 
     createdAt: number; value?: T }.

     Regras:

     - begin marca in-flight e devolve { status: 'new' } quando a chave não
       existe.
     - Chave existente com fingerprint diferente → fingerprint-mismatch (mesma
       chave usada
       para outro pedido: erro de cliente, não pode virar replay de um pedido
       que não é aquele).
     - Chave in-flight → in-flight. Chave completed → replayed com o valor
       guardado.
     - complete(key, value) grava o resultado; release(key) apaga a entrada.
     - createdAt é gravado só no begin e nunca atualizado, então a ordem de
       inserção do Map
       continua monotônica em createdAt.

     Contenção de memória, sem setInterval (evita segurar o event loop e vazar
     entre testes):

     - TTL padrão de 10 min. Varredura preguiçosa no início de cada begin: itera
       o Map na
       ordem de inserção e break no primeiro item não expirado.
     - Teto padrão de 1000 entradas: ao inserir acima do teto, remove a mais
       antiga (primeira
       chave do Map). Sem isso um cliente malicioso enche a memória com chaves
       aleatórias.

     ttlMs/maxEntries pelo construtor existem para o spec exercitar expiração e
     evicção sem
     fake timers.

     Novo: apps/api/src/common/idempotency-store.spec.ts — begin
     novo/in-flight/replay;
     mismatch de fingerprint; release libera a chave para um novo begin; entrada
     expirada por
     TTL vira new; passar do maxEntries descarta a mais antiga.

     Header ausente → o schema recebe undefined → 400. Chave passa a ser
     obrigatória.
     (req.headers do Express é minúsculo, então 'idempotency-key' casa com
     qualquer
     capitalização enviada pelo cliente.)

     apps/api/src/checkout/checkout.service.ts — o corpo atual vira um
     #execute(dto)
     privado, intocado, e o purchase público ganha a camada de idempotência:

     private readonly idempotency = new IdempotencyStore<CheckoutResult>();

     purchase(dto: CheckoutDto, idempotencyKey: string): CheckoutResult {
       const fingerprint = `${dto.productId}:${dto.quantity}`;
       const begin = this.idempotency.begin(idempotencyKey, fingerprint);

       if (begin.status === 'replayed') return begin.value;
       if (begin.status === 'in-flight')
         throw new ConflictException('Esta compra já está em processamento');
       if (begin.status === 'fingerprint-mismatch')
         throw new UnprocessableEntityException(
           'Este Idempotency-Key já foi usado para outra compra',
         );

       try {
         const result = this.execute(dto);
         this.idempotency.complete(idempotencyKey, result);
         return result;
       } catch (error) {
         this.idempotency.release(idempotencyKey);   // falha não "queima" a 
     chave
         throw error;
       }
     }

     Duas escolhas que vale registrar:

     - Falha libera a chave. Guardar o erro no store deixaria o cliente preso a
       um 409 de
       estoque que talvez já não seja verdade. Como o front gera chave nova
       depois de um erro de
       negócio (§4), na prática a entrada só some para não ocupar espaço.
     - O in-flight hoje nunca é observável, porque purchase é 100% síncrono: o
       begin/complete acontecem no mesmo tick, sem await no meio — a mesma
       propriedade que já
       torna o decremento de estoque atômico. O caminho existe para o dia em que
       o checkout virar
       assíncrono (gateway de pagamento) e continua correto desde já; o custo
       são ~4 linhas.

     UnprocessableEntityException (422) separa "chave reciclada para outro
     pedido" do 409 de
     estoque insuficiente — os dois já caem no mesmo tratamento genérico de 4xx
     do
     toHttpError em client.ts:66, então nada muda no front.

     apps/api/src/checkout/checkout.service.spec.ts — casos novos, no padrão
     pt-BR do
     arquivo: mesma chave duas vezes → mesmo orderId e estoque cai uma vez;
     chaves
     diferentes → duas compras; mesma chave com quantity diferente → 422; compra
     que falha por

     4. Web — chave por tentativa

     Novo: apps/web/src/api/idempotency.ts — a regra de ciclo de vida da chave
     como função
     pura, para ser testável sem jsdom/Testing Library (o vitest.config.ts do
     web é
     environment: 'node' e não há infra de teste de componente):

     export interface PurchaseAttempt { key: string; fingerprint: string }

     export function checkoutFingerprint(productId: string, quantity: number):
     string;

     /** Reusa a chave da tentativa atual; gera outra se não houver ou se o 
     pedido mudou. */
     export function resolveAttempt(
       current: PurchaseAttempt | null,
       fingerprint: string,
       newKey: () => string,
     ): PurchaseAttempt;

     O fingerprint do lado do cliente é o detalhe que evita o 422 na prática: se
     o usuário toma
     um erro de rede e então muda a quantidade antes de tentar de novo,
     resolveAttempt vê
     fingerprint diferente e emite chave nova, em vez de mandar a chave antiga
     com outro payload.

     apps/web/src/api/client.ts — postCheckout ganha um terceiro parâmetro:

     export function postCheckout(

     O helper request<T> e o tratamento de erro ficam intactos.

     apps/web/src/components/BuyForm.tsx — a tentativa vira um
     useRef<PurchaseAttempt | null>,
     logo após a validação do Zod que já existe (linha 30-36):

     - const attempt = resolveAttempt(attemptRef.current, 
       checkoutFingerprint(productId, parsed.data), () => crypto.randomUUID()),
       guardado no ref e enviado no postCheckout.
     - Sucesso → attemptRef.current = null (próximo clique é uma tentativa
       nova).
     - Erro com error.retryable === false (400/404/409/422 — desfecho
       definitivo) → também
       zera o ref.
     - Erro retryable (rede, timeout, 5xx — não se sabe se a API processou) →
       mantém o ref, e
       o próximo clique reenvia a mesma chave; se a compra tinha ido, a API
       devolve o mesmo
       201 e o estoque não cai de novo.

     O isSubmitting continua exatamente como está — vira a primeira linha de
     defesa, com o
     servidor por trás. crypto.randomUUID() exige contexto seguro; localhost e
     HTTPS contam,
     então dev e prod estão cobertos.
