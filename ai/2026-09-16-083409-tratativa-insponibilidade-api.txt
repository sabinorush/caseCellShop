     Tratativa de erro de ambiente (API) e de indisponibilidade (Web)

     Context

     Hoje o projeto falha feio nos dois extremos do fluxo:

     1. API — apps/api/src/main.ts:5 chama loadEnvFile('.env') no topo do
        módulo, sem try/catch. Como só o .env.example é versionado, quem clona o
        repo recebe um ENOENT com stack trace do Node e nenhuma pista do que
        fazer. Além disso process.env.PORT ?? 3000 passa a string crua para
        app.listen() — um PORT=abc só quebra lá na frente, com erro obscuro.
     2. Web — apps/web/src/api/client.ts só cria ApiError quando !response.ok.
        Falha de rede (fetch rejeita) e payload fora do schema escapam como
        TypeError/ZodError e caem no fallback genérico de App.tsx/BuyForm.tsx.
        Quando a API está fora, o proxy do Vite devolve 502 text/plain com corpo
        vazio, então parseErrorMessage cai no default e o usuário lê "Erro 
        inesperado (HTTP 502)" — sem explicação e sem saída.

     Objetivo: a API falha cedo e com mensagem acionável quando o ambiente está
     errado; o front distingue indisponibilidade do servidor de erro de negócio
     e oferece "Tentar novamente".

     Decisões confirmadas: falhar sempre quando o .env estiver ausente ou
     inválido; simular a queda via handler de erro no proxy do Vite (502/504);
     adicionar Vitest ao apps/web para cobrir o client.ts; incluir botão de
     retry na UI.

     1. API — validação de ambiente com early return

     Novo: apps/api/src/config/env.ts

     checkout.schema.ts); não instalar @nestjs/config.

     async function bootstrap() {

     esvaziar antes de sair.

     porta X já está em uso") no mesmo formato, evitando o único outro stack

     2. Web — proxy do Vite devolvendo 502/504 reais

     apps/web/vite.config.ts

     a) Validar API_URL. Hoje, se estiver ausente, target vira undefined e o
     Vite estoura com erro interno. Validar com zod (z.url()) e lançar Error com
     mensagem em pt-BR apontando o .env.example.

     b) Handler de erro no proxy. Verifiquei o Vite 8.3.0 instalado
     (dist/node/chunks/node.js:19380-19395): opts.configure(proxy, opts) roda
     antes do handler interno do Vite, e o interno só escreve se
     !res.headersSent. Ou seja, o nosso handler ganha a resposta:

     configure: (proxy) => {
       proxy.on('error', (err: NodeJS.ErrnoException, _req, res) => {
         if (!('req' in res)) { res.destroy(); return; }          // upgrade de 
     websocket
         if (res.headersSent || res.writableEnded) { res.end(); return; }
         const status = TIMEOUT_CODES.has(err.code ?? '') ? 504 : 502;
         res.writeHead(status, { 'Content-Type': 'application/json; 
     charset=utf-8' });
         res.end(JSON.stringify({ statusCode: status, message: 'API 
     indisponível' }));
       });
     },
     timeout: 10_000,
     proxyTimeout: 10_000,

     Mapeamento: ECONNREFUSED / ENOTFOUND / EHOSTUNREACH / EAI_AGAIN → 502 (API
     não está no ar); ETIMEDOUT / ECONNRESET / ECONNABORTED → 504. O ECONNRESET
     entra em 504 porque proxyTimeout é implementado como proxyReq.destroy()
     (node.js:18745), que emite exatamente esse código.

     Ganho duplo: derrubar a API passa a produzir um 502 com corpo JSON (em vez
     de 502 text/plain vazio), e o dev passa a espelhar o que um reverse proxy
     faria em produção.
