     CaseCellShop — Setup inicial do monorepo

     Context

     O diretório C:\Users\gusab\projects\CaseCellShop contém apenas o PRD.md.
     Não há código, nem repositório git. O objetivo é criar do zero um monorepo
     pnpm com uma loja mínima de capas de celular que permita testar ponta a
     ponta o fluxo de compra e as três regras de negócio do PRD (estoque não
     pode ser estourado, estoque só cai em compra bem-sucedida, botão não pode
     enviar duas vezes).

     Decisões confirmadas com o usuário:
     - Compra direta de 1 produto (sem carrinho): lista → escolhe quantidade →
       botão Comprar.
     - Sem formulário de dados do cliente: o checkout envia só productId +
       quantity. O Zod valida a quantidade (inteiro, ≥ 1, ≤ estoque) no front e
       o payload no back.
     - Testes só no back-end, com o Jest que já vem no Nest.
     - UI em pt-BR, código/rotas em inglês.

     Fora de escopo (PRD): auth, gateway de pagamento, banco persistente,
     deploy, docker, layout elaborado.

     Passo 1 — Scaffolding

     1. git init na raiz + .gitignore (node_modules, dist, .env*, logs).
     2. pnpm-workspace.yaml com packages: ["apps/*"]; package.json raiz privado
        com os scripts acima.
     3. API: pnpm dlx @nestjs/cli new api --package-manager pnpm --skip-git 
        --skip-install dentro de apps/, depois pnpm dlx @nestjs/cli generate 
        resource checkout e ... generate resource products (REST, sem CRUD
        completo — vou enxugar os handlers gerados que não uso).
     4. Web: pnpm create vite@latest web --template react-ts dentro de apps/.
     5. Renomear os pacotes para @casecellshop/api e @casecellshop/web; garantir
        script dev em cada um (nest start --watch / vite).
     6. Instalar zod nos dois apps.

     Passo 2 — Back-end (apps/api)

     Catálogo em memória — src/products/products.data.ts: ~6 capas com id, name,
     model, priceCents, stock. Preço em centavos (inteiro) para não ter float
     em dinheiro.

     - products.service.ts: guarda o array como estado mutável do singleton;
       expõe findAll(), findOne(id) e decreaseStock(id, quantity). Toda a lógica
       de estoque vive aqui — é o único ponto que muta o array.
     - products.controller.ts: só GET /products.
     - checkout.service.ts: recebe { productId, quantity }, busca o produto (404
       NotFoundException se não existir), e chama decreaseStock. A checagem
       quantity > stock e o decremento ficam no mesmo bloco síncrono, sem await
       no meio — como o Node é single-threaded, isso torna a operação
       efetivamente atômica e duas requisições simultâneas não conseguem
       estourar o estoque. Se faltar estoque → ConflictException (409) e nada é 
       decrementado.
     - Retorno do POST /checkout (201): { orderId, productId, productName, 
       quantity, unitPriceCents, totalCents, remainingStock }. orderId via
       randomUUID().
     - Zod no Nest: um ZodValidationPipe genérico em
       src/common/zod-validation.pipe.ts que recebe um schema, roda safeParse e
       lança BadRequestException (400) com os issues formatados. Aplicado no
       @Body() do checkout com o schema de src/checkout/checkout.schema.ts
       (productId: string min 1, quantity: int positivo, max razoável). Tipo do
       DTO inferido com z.infer.
     - main.ts: app.enableCors() (a UI usa proxy do Vite, mas o CORS deixa a API
       testável direto pelo navegador/curl) e porta 3000.

     Testes (Jest)
     - checkout.service.spec.ts: compra válida retorna total certo e reduz o
       estoque; quantity > stock lança 409 e o estoque permanece intacto (a
       regra 2 do PRD); produto inexistente lança 404; compras sequenciais até
       zerar o estoque funcionam e a seguinte falha.
     - products.service.spec.ts: findAll devolve o catálogo; decreaseStock
       rejeita quantidade maior que o estoque.
     - checkout.schema.spec.ts: rejeita quantidade 0, negativa, fracionária e
       não-numérica.
     - test/app.e2e-spec.ts: GET /products → 200 com lista; POST /checkout feliz
       → 201; payload inválido → 400; estoque insuficiente → 409.
     - Cada suíte reconstrói o módulo de teste para partir de um catálogo limpo
       (seed exportado como função createProducts() que devolve uma cópia nova,
       evitando vazamento de estado entre testes).

     Passo 3 — Front-end (apps/web)

     - vite.config.ts: proxy /api → http://localhost:3000 (evita lidar com
       CORS/URLs em dev).
     - src/api/client.ts: getProducts() e postCheckout() com fetch; parseia a
       resposta com schemas Zod (src/api/schemas.ts) para validar também o que
       vem da API; erros HTTP viram uma ApiError com a mensagem do back.
     - src/App.tsx: carrega os produtos no mount, renderiza a grade e um banner
       de sucesso/erro.
     - src/components/ProductCard.tsx + ProductCard.module.css: nome, modelo,
       preço formatado (Intl.NumberFormat pt-BR), estoque e o formulário de
       compra.
     - src/components/BuyForm.tsx: input numérico de quantidade + botão Comprar.
       - Validação com Zod no submit (quantitySchema(stock)): mensagens em pt-BR
         ("Informe uma quantidade válida", "Quantidade maior que o estoque
         disponível").
       - Anti-duplo-envio: estado isSubmitting; o handler retorna cedo se já
         estiver enviando, o <button disabled={isSubmitting}> muda o texto para
         "Comprando…", e o finally religa. Produto sem estoque → botão
         desabilitado com "Esgotado".
       - Após sucesso, o stock do produto é atualizado no estado do App com o
         remainingStock devolvido pela API (fonte da verdade é o back).
     - Estilos com CSS Modules apenas (*.module.css), layout simples em grid,
       sem biblioteca de UI.

     Arquivos críticos

     - apps/api/src/products/products.service.ts — dono do estoque; onde as
       regras 1 e 2 são garantidas.
     - apps/api/src/checkout/checkout.service.ts — orquestra a compra e mapeia
       os erros de domínio para 404/409.
     - apps/api/src/common/zod-validation.pipe.ts — ponte Zod ↔ Nest.
     - apps/web/src/components/BuyForm.tsx — onde a regra 3 (sem envio
       duplicado) é garantida.
     - package.json (raiz) e pnpm-workspace.yaml — atalhos com --filter.

     Verificação

     1. pnpm install na raiz; pnpm test:api → todas as suítes passando.
     2. pnpm dev e abrir http://localhost:5173: a grade de produtos carrega.
     3. Comprar 1 unidade → banner de sucesso e o estoque no card cai.
     4. Tentar comprar mais do que o estoque → erro em pt-BR e o estoque não 
        muda (confirmar com curl http://localhost:3000/products).
     5. Zerar o estoque de um produto → botão vira "Esgotado".
     6. Duplo-clique rápido no Comprar → o botão trava em "Comprando…" e só uma
        requisição sai (conferir na aba Network).
     7. curl -X POST http://localhost:3000/checkout -H "Content-Type: 
        application/json" -d '{"quantity":0}' → 400 com os erros do Zod.
